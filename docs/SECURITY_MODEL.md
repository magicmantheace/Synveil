# Synveil Security Model

Status: **initial threat model**

## Security premise

A capable AI planner is still untrusted with respect to system authority.

Synveil assumes that a model can:

- misunderstand user intent,
- hallucinate system state,
- produce malformed plans,
- be influenced by hostile content,
- optimize the wrong objective,
- become unavailable,
- be replaced by a different model with different behavior.

Security therefore cannot depend on the planner "being careful."

## Trust boundaries

### Trusted computing/control base

The smallest practical deterministic set:

- kernel and essential platform firmware assumptions,
- boot verification components when introduced,
- veil-core,
- veil-policy,
- action validators,
- veil-executor,
- transaction/audit integrity code,
- recovery mechanisms.

### Untrusted or less-trusted

- veil-planner/model output,
- external content,
- web pages,
- documents and prompts,
- application text,
- inferred user preferences,
- third-party plugins/integrations,
- remote model output,
- telemetry labels generated by probabilistic models.

## Core defenses

### No generic privileged execution tool

Production AI paths must not expose an unrestricted root command runner.

Privileged behavior is implemented as versioned capabilities.

### Validate twice

Action data should be schema-valid before policy evaluation and validated again against live system preconditions immediately before execution.

### Least authority

Each service should run with the minimum privilege it requires. Long-term design should use Linux capabilities, service isolation, namespaces/cgroups, seccomp, or equivalent controls where they materially reduce risk.

### Approval cannot be inferred

A user saying "I like performance" is not authorization to disable security controls, destroy data, or install arbitrary software.

### Prompt/data separation

Text observed from applications, websites, logs, filenames, package metadata, or documents is data, not authority. It must not be able to promote itself into system instructions.

### Durable audit

Every privileged action should be attributable to:

- initiating user/system goal,
- proposed plan,
- policy result,
- exact parameters,
- execution result.

### Recovery independent of the model

The user must be able to disable AI components and recover the machine without successfully running inference.

## Action-risk examples

### Typically low risk

- reading metrics,
- collecting permitted system state,
- workload-scoped CPU scheduling hints,
- expiring process-priority adjustments within configured bounds.

### Medium risk

- persistent sysctl tuning,
- changing service start policy,
- persistent power-management profiles,
- cache configuration.

### High risk

- installing/removing system packages,
- kernel/driver changes,
- bootloader mutation,
- firewall/security configuration,
- account/permission changes.

### Destructive/security critical

- deleting user data,
- filesystem formatting/repartitioning,
- disabling authentication/security boundaries,
- modifying trusted keys,
- weakening verified boot,
- exposing private services publicly.

Risk classification is determined by deterministic policy, not by planner self-assessment.

## Initial developer rule

During bring-up, developer scripts may use shell/root privileges to construct and test images. Those scripts are not evidence that the final AI execution path may do the same.

Developer authority and autonomous runtime authority are separate concerns.
